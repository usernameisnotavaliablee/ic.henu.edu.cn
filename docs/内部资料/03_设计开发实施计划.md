# 设计开发实施计划

更新：2026-10-09｜MVP：2026-10-15｜上线：2026-10-18

## 一、目标、前提和当前阶段

目标是在学院确认的范围内完成可访问MVP、审核修改、正式上线和基本交接。

当前处于“资料与需求确认、现有工程交接、网站调研”阶段。两位开发者每人每天不足两小时，优先复用学长工程和校方现有能力。源码预计可取得但尚未交付；平台路径、后台需求、首版范围和正式上线口径尚未确认。

本计划安排执行顺序、责任与完成条件，不提前替学院决定首版栏目，也不预先指定前后端技术栈或数据库。

## 二、流程与每阶段交付

### 阶段1：收资料、锁范围、确定平台

输入：现有素材清单、补充清单、老师答复、学长源工程和学校申请路径。

工作：
- 确认唯一反馈汇总人、需求拍板人、内容审核人和发布确认人。
- 整理首版页面/功能清单，逐项标注“首版、后续、暂不需要”。
- 明确15号和18号分别怎样验收，是否允许测试链接用于15号演示。
- 获取学长工程并按说明运行，核实搜索、新闻、教师、双语等功能。
- 由学院或获授权人员推进学校申请，记录办理节点。

输出：首版确认表、可运行工程、复用/缺失功能表、平台决定与申请进度。
完成标准：开发者知道做哪些页面和功能、在哪发布；尚未确定的事项有负责人和决定时间。

### 阶段2：设计信息结构和页面

按以下顺序完成，避免先画很完整的页面后再推倒：

1. 页面结构：导航、栏目、列表/详情关系、外部链接。
2. 内容映射：每页需要什么内容、谁提供、当前是否齐全；材料不足的页面单列待处理。
3. 低保真原型：首页及实际需要的通用内页，先确认信息先后顺序和交互。
4. 视觉稿：复用现有模板，替换为集成电路主题，确认校院标识、主色、图片和文字层级。
5. 手机布局：确定菜单、长名称、教师卡片、正文图片和表格在小屏下的方式。
6. 数据与维护设计：明确内容如何进入页面、如何修改与发布。

平台决定后的处理：
- **学校网站群**：设计栏目树、内容类型、模板和组件映射，确认编辑/审核/发布权限；数据库通常由平台管理。
- **已有独立项目**：沿用其技术栈、后台和数据库，明确需要新增或调整的字段、接口与权限。
- **现有能力无法满足已确认需求**：列出缺口和影响，由负责人决定缩小首版或后续开发，不默认在剩余工期内从零重建。

输出：页面结构图、首页与通用内页设计、手机布局、内容字段表、平台/接口说明。
完成标准：关键页面和功能已确认，剩余细节可以在明确规则下实现，不需要边写代码边猜业务。

### 阶段3：开发与内容录入

实施顺序：
1. 公共部分：校院标识、导航、页脚、基础样式和手机导航。
2. 内容模板：实现确认范围中的介绍、师资、新闻/通知等页面类型。
3. 数据接入：配置校方组件，或接入现有项目接口；只实现首版已确认功能。
4. 内容录入：只把审核通过的材料标为可发布；测试占位内容单独标注。
5. 自检：旧学院名称、联系人、教师、图片、链接和语言残留检查。
6. 每完成一类页面就部署测试版并复核，避免集中到最后一天集成。

输出：可访问的测试版本、版本记录、已完成清单和剩余问题。
完成标准：主要流程真实可用，界面元素没有被误当作已实现功能。

### 阶段4：MVP验收与反馈

15号提交测试链接、页面清单、已完成内容和明确的未完成项。由同一位联系人汇总反馈，并区分：
- 发布前必须修复的问题；
- 首版已确认范围内的调整；
- 后续迭代的新需求。

输出：一份有负责人和处理结果的反馈清单。
完成标准：学院知道当前版本能做什么、哪些内容待审，以及18号发布需要解决什么。

### 阶段5：上线与交接

- 完成正式材料审核，清除测试内容和无效入口。
- 验证正式域名、HTTPS、路径、附件、手机访问及管理员操作。
- 保存发布前备份，记录当前版本和回滚步骤。
- 完成校方要求的检查，由学院确认发布。
- 如有后台，提供与实际功能对应的编辑、审核、发布说明。

输出：正式站点、发布记录、源工程交接说明、更新与恢复说明、维护联系人。
完成标准：正式地址可用、内容已确认、维护人员能完成约定的更新工作。

## 三、两人协作方式

| 角色 | 主责 | 具体交付 |
|---|---|---|
| 你 | 学院对接、业务决策、材料整理与内容验收；配合AI推进页面 | 确认表、素材状态、合并后的老师反馈、页面与文字验收结果 |
| 队友 | 源码交接、环境和平台对接、技术集成与发布 | 可运行工程、复用核验、部署步骤、版本与回滚记录 |
| AI | 调研整理、源码分析、原型与方案草案、编码和排查、验证辅助 | 可审阅方案、代码、问题记录和文档；执行以当时可用权限与环境为准 |

- 一个共享仓库，每个任务一个主要负责人；队友负责主分支合并和发布。
- 拿到工程后按模块拆分，双方避免同时改公共模板或同一组件。
- 每天约10分钟同步“完成、阻塞、下一步”。记录工作时长，超出剩余时间的内容及时交由负责人决定。
- 学院事实与发布决定由人确认；AI整理、实现和检查不替代业务批准。

## 四、日期安排与依赖

| 时间 | 工作重点 | 当日应得到的结果 |
|---|---|---|
| 10月9—10日 | 补充清单、调研、源码交接、学校申请对接 | 源工程交接安排、首版确认进展、申请人和平台路径 |
| 10月11日 | 运行工程、核验复用能力、完成关键设计并确认 | 可运行基线、页面/功能清单、首页与通用内页方案 |
| 10月12—13日 | 复用改造、平台/数据接入、录入审定内容 | 连通主要页面的测试版 |
| 10月14日 | 内容、链接、手机和必要功能检查 | 可提交MVP的版本及明确的剩余事项 |
| 10月15日 | MVP演示与统一反馈 | 学院反馈清单和18号发布剩余工作 |
| 10月16日 | 修复反馈、补齐正式内容和环境 | 发布候选版本 |
| 10月17日 | 正式环境验证、校方检查、备份和发布确认 | 可上线版本及恢复方案 |
| 10月18日 | 按确认口径上线、演示保障 | 正式发布记录和维护交接 |

日期是工作目标，依赖学院反馈、源码交接和校方办结时间。每人每天不足两小时，首版规模必须匹配实际剩余工时。

关键依赖的处理：
- 10月11日仍拿不到工程：当天说明影响；继续内容和页面结构工作，不擅自承诺从零补齐原项目。
- 平台路径未确认：可做内容与视觉设计，但不先建设一套假定的后台。
- 材料未审定：在测试版标注；正式发布前采用学院明确同意的隐藏/替代安排。
- 正式环境或域名未办结：测试链接不自动算正式上线，由负责人确认替代交付口径。
- 全量官网调研继续补齐；调研进度与开发进度分别记录，新发现不会自动扩大已确认首版。

## 五、验收清单

### 内容与页面
- 名称、教师身份/职称、研究方向、课程和联系方式经确认。
- 正式版本无旧学院残留、假新闻、未标识的占位内容及无效菜单。
- 确认范围中的列表、详情、外链和附件能正常打开。
- 电脑和手机检查菜单、长标题、图片、文字、表格及横向溢出。
- 如做双语，两种语言均有审定内容，切换后不混用旧学院信息。

### 功能与基础防护
- 搜索、表单、下载、筛选等仅在纳入首版时测试；搜索要能返回实际结果。
- 如有后台，验证登录、退出、权限及编辑—审核—发布流程。
- 如有数据库查询，检查参数化处理；页面按输出位置编码，有富文本时净化。
- 如有上传，核对权限、允许的文件类型及大小；不只依赖拦截几个Payload。
- 安全检查在自有测试环境或获授权环境进行；其他学院网站仅作公开资料调研。

### 部署与交接
- 正式域名、HTTPS、资源路径和校方网络访问通过验证。
- 确认重启或重新发布后站点可用，上传文件等持久数据保留。
- 独立项目验证备份恢复；平台模式核对平台备份/版本恢复与管理员操作。
- 记录发布版本、回滚办法、维护联系人，交付必要的更新说明。

## 六、最小学习路径

不先学习一整套新框架。拿到工程后依次掌握：

1. 启动、构建、配置、看日志。
2. Git分支、提交、合并和回退。
3. 当前项目的公共模板与页面内容修改方式。
4. 学校平台的栏目、组件、编辑和发布；若是独立项目，再补其接口与数据库流程。
5. 手机调试、链接与内容检查、部署和恢复。

设计阶段的最终标志是“页面、内容、维护方式与技术路径足够明确，可以直接实现”，不是先画完所有数据库表或把原素材清单全部收齐。
